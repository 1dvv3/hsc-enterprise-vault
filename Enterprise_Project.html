2. Identifying and Defining

2.1 Tools and Processes for Managing and Documenting Development

Tool / process Purpose
Problem definition States clearly what the system must solve, before any solution is designed
Time and resource management, incl. Gantt charts Schedules tasks, milestones and deadlines, showing which activities run concurrently
An iterative approach Building in repeated cycles, refining with each pass rather than completing everything once
Production process and technical skills The methods and capabilities required to actually build the system
Testing and evaluation Verifying the system works and judging whether it met its purpose

2.2 The Changing Nature of Enterprise

Change Effect on project development
Offshore development Work contracted to teams overseas — lower cost, but time-zone, communication and quality-control challenges
Working remotely Teams distributed rather than co-located — requires online collaboration tools and clear documentation
Freelance work Specialist skills engaged per-project rather than employed — flexible and cost-effective, but less continuity
Enabling the growth of start-ups Low-cost cloud infrastructure and remote talent let small enterprises build systems that once required large capital

3. Researching and Planning

3.1 Tools Supporting Design and Development

Tool What it does
Online collaboration Shared documents, version control and communication across a distributed team
Time / task action plans Break the project into scheduled tasks with owners and deadlines
Process diary, incl. ongoing evaluation Running record of decisions, problems and changes — evidence of the iterative process
Budget Costs the resources, licences, hardware and labour required
System flowcharts Show the logical steps the system performs
Data flow diagrams Show how data moves between entities, processes and stores
Decision trees Represent logical decision-making as branching conditions and outcomes

Confusing pair — System flowchart vs Data flow diagram A flowchart shows the sequence of logic — what happens, in order, with decisions. A DFD shows where data goes — sources, processes, stores and destinations. Flowchart = how it thinks. DFD = where information travels.

3.2 Thinking Skills

Skill Applied to
Computational thinking Decomposition, pattern recognition, abstraction, algorithms — see Intelligent Systems §7
Design thinking Understanding users and iterating solutions — see §4.3 below
Systems thinking Seeing how components interact as a whole rather than in isolation

3.3 Collaborating and Managing Criteria

Criterion Meaning
Designing for ease of operation and maintenance Building so that non-experts can run it and future developers can modify it
Clarifying each of the relevant informatics within the new system Identifying what information the system handles and how it transforms it
Outlining the role of participants, data and components Who does what, what data flows where, which components are responsible
Negotiating user/client needs and wants Distinguishing what the client needs from what they want, within budget and time
Working collaboratively Shared responsibility, clear communication, agreed processes

4. Producing and Implementing

4.1 Tools to Inform Requirements and Limitations

Tool Strength
Interviews Deep, qualitative understanding of individual user needs
Surveys Broad, quantitative data from many users quickly
Analytical reports Existing documented evidence about the problem domain
Prototypes A working model users can react to — surfaces requirements they couldn't articulate
Presentations of research results Communicates findings to stakeholders and secures agreement

4.2 Development Approaches

Approach How it works Best for
Waterfall (structured) Linear and sequential — each phase completes before the next begins Well-defined, stable requirements; safety-critical work
Agile Iterative and incremental — repeated short cycles with continuous client involvement Evolving requirements; fast-moving projects
Prototyping Build a working model early, refine it based on feedback When requirements are unclear and users need something to react to
End-user The users themselves develop the system, typically with spreadsheets or low-code tools Small, local solutions where users know the problem best
Outsourcing Development contracted to an external provider When the skills don't exist in-house, or cost favours it

Confusing pair — Waterfall vs Agile Waterfall fixes requirements at the start; working software appears only at the end; changing late is very costly. Agile expects requirements to change; working software appears every iteration; total cost and time are harder to predict.

4.3 Design Thinking

1. EMPATHISE   understand the needs and challenges of end-users
2. DEFINE      state the problem clearly
3. IDEATE      generate possible solutions
4. PROTOTYPE   build a testable model of the solution
5. TEST        evaluate with real users and iterate

A prototype's purpose is to test ideas and gather feedback before committing to full development, reducing the risk of building the wrong thing.

4.4 Risk Analysis

Risk analysis identifies what could go wrong during a project so those risks can be prevented or mitigated before they occur, rather than reacted to afterwards.

Risk type Examples
Security risks Data breach, unauthorised access, malware
Technical risks Hardware failure, integration incompatibility, data loss
Financial risks Budget overrun, unexpected licensing costs
Time / scheduling risks Missed deadlines, dependency delays, scope creep
Human risks Staff turnover, insufficient training, user resistance

Reducing security risk: encryption, access control and authentication, regular backups, staff training, security audits.

4.5 Hardware and Software Integration

Why it matters: new components must work with the existing enterprise environment, or the system fails at deployment regardless of how well it was built.

What to consider:

  • Compatibility with existing hardware, operating systems and software
  • Data migration — can existing data be transferred without loss?
  • Interoperability — will the new system exchange data with current systems?
  • Capacity — can existing infrastructure handle the additional load?
  • Cost of any required upgrades

4.6 Training

Why train before implementation: users who don't understand the system make errors, resist the change, and undermine the return on the investment. Training reduces errors, increases adoption and shortens the productivity dip after go-live.

Methods: face-to-face workshops · online modules and tutorials · user manuals and documentation · mentoring by a super-user · help desk support.

4.7 System Implementation Methods

Method How it works Risk
Direct Old system switched off, new one switched on — a straight swap across the whole organisation at once Highest risk — no fallback. Cheapest and fastest
Parallel Old and new systems run together for a period Lowest risk — the old system is a fallback. Most expensive, duplicated effort
Pilot New system trialled with a small group first, then rolled out Low risk, limited disruption if it fails
Phased Introduced one module or department at a time Moderate risk, slower, integration complexity during transition

The recommendation questions they ask: Hospital management system → parallel. Patient safety means you cannot afford a gap; the cost of duplication is justified by the consequence of failure. Banking system → parallel over direct, for the same reason — financial records cannot be lost or corrupted, and a fallback is essential.

4.8 Testing Methodologies

Methodology What it checks
Functional testing That every function of the system performs correctly against its specification
Live data The system using real operational data to validate behaviour
Simulated data Artificially created data, including edge cases that rarely occur naturally
Beta testing Real users evaluate the system before full release
Volume testing Whether the system handles very large amounts of data without performance loss
Acceptance testing The client confirms the system meets their requirements

Why use multiple methodologies rather than one: each detects a different class of fault. Functional testing finds logic errors but not performance problems. Volume testing finds scaling problems but not usability problems. Beta testing finds usability problems but not edge cases. Relying on one leaves whole categories of defect undetected.

5. Testing and Evaluating

5.1 Verification vs Validation

Question it answers Meaning
Verification Are we building the system right? Does it meet the specifications? Is it free of defects?
Validation Are we building the right system? Does it meet the user's actual needs and solve the real problem?

A system can be perfectly verified — flawlessly built to spec — and completely fail validation, because the spec described the wrong thing.

5.2 The Five Evaluation Activities

Activity Purpose
Evaluating test data Confirms the system produces correct output across normal, boundary and invalid inputs before deployment
Trialling operation and maintenance documentation Ensures the documentation actually works for the people who will run and maintain the system — supports long-term success after the developers leave
Reviewing the impact of implementation Assessing effects across the organisation — see §5.3
Modifying designs to improve functionality Using user feedback to identify shortcomings and refine the system
Testing, evaluating and maintaining Ongoing after deployment, not a one-off event

5.3 Reviewing Organisational Impact

Aspect How it may be affected
Employees New skills required, changed roles, resistance, possible displacement
Processes and workflows Tasks performed differently, some eliminated, new steps introduced
Customers and clients Service speed, accuracy and experience change
Finances Implementation and training costs against efficiency gains
Data and information New data collected, new storage and security obligations
The environment Energy consumption, hardware disposal, reduced paper use

5.4 Test Data Categories

Category Definition Example (age must be 0–120)
Normal / valid Typical expected values 25
Boundary Values at the edges of the valid range 0, 120
Extreme / invalid Values outside the range, or the wrong type −5, 200, "abc"

Why each matters: normal data proves the system works in ordinary use. Boundary data catches off-by-one errors, the most common logic fault. Invalid data proves the system rejects bad input gracefully rather than crashing.

5.5 Why Continuous Testing After Deployment

  • Requirements change as the enterprise changes
  • The operating environment changes — new hardware, operating systems, integrations
  • New defects surface only under real-world load and unusual conditions
  • Security threats evolve, so what was secure at launch may not remain so
  • User feedback reveals usability problems invisible during development

  2. Which stage involves generating possible solutions?

Thinking and design tools

  1. Which tool visualises how users interact with a system?
  2. Which project management tool schedules tasks, milestones and deadlines?
  3. Which thinking tool represents logical decision-making processes?

Risk analysis

  1. What is the purpose of conducting a risk analysis?
  2. Identify four common types of risk.
  3. Name one strategy to reduce security risks.

Integration and training

  1. Why is hardware and software integration important?
  2. What should be considered when integrating new software with existing systems?
  3. Why should end-users receive training before implementation?
  4. Suggest two training methods.

Implementation methods

  1. Which method introduces the system to the entire organisation at once? → Direct
  2. Which allows old and new to operate together? → Parallel
  3. Which introduces it to a small group first? → Pilot
  4. Which introduces it one module or department at a time? → Phased

Testing methodologies

  1. Which checks every function performs correctly? → Functional
  2. Which uses real operational data? → Live data
  3. Which uses artificially created data? → Simulated data
  4. Which allows real users to evaluate before release? → Beta
  5. Which determines whether the system handles very large data volumes? → Volume

Extension — higher order

  1. Which implementation method for a hospital management system? Justify.
  2. Why is risk analysis important in an implementation plan?
  3. How does design thinking contribute to successful development?
  4. Why is user training essential?
  5. Compare parallel and direct implementation. Which for a banking system, and why?
  6. Why include multiple testing methodologies rather than one?

Testing and evaluating

  • What is the difference between verification and validation?
  • Why evaluate test data before deployment?
  • Identify four types of test data and explain why each matters.
  • How does trialling maintenance documentation support long-term success?
  • What aspects of the organisation should be evaluated after implementation?
  • How can user feedback modify design and improve functionality?
  • Why do systems require continuous testing, evaluation and maintenance?

7. Confusing Terms — Quick Reference

Term Meaning Don't confuse with
Verification Built right — meets the spec Validation — the right system, meets user needs
Direct implementation Whole organisation at once, no fallback Parallel — both run together
Pilot Small group of users first Phased — one module or department at a time
Waterfall Linear, sequential, fixed requirements Agile — iterative, expects change
Prototyping Build a model to clarify requirements Agile — a whole development methodology
Functional testing Every function against spec Acceptance testing — the client confirms
Live data Real operational data Simulated data — artificially generated
Boundary data At the edges of valid range Invalid data — outside the range
System flowchart Sequence of logic DFD — movement of data
Gantt chart Tasks, milestones, deadlines over time Decision tree — branching logic
Needs What the client must have Wants — what they would like
Offshore development Work sent overseas Outsourcing — contracted externally, may be local
